这是一个基于 MySQL 的详细数据库表结构设计。

设计遵循了**“T1-T5 等级制度”**、**“不转存文件（直接存上游链接）”**、**“高并发任务管理”**以及**“积分资产安全”**的核心需求。

---

### 1. 用户与权限核心表
#### 表名：`users` (用户表)
**描述**：存储用户基础信息、当前等级、积分余额。

| 字段名 | 类型 | 属性 | 描述 |
| --- | --- | --- | --- |
| `id` | INT | PK, AI | 用户唯一 ID |
| `email` | VARCHAR(100) | UK, Not Null | 登录邮箱 (唯一索引) |
| `password_hash` | VARCHAR(255) | Not Null | 加盐加密后的密码 |
| `balance` | DECIMAL(10, 2) | Default 0.00 | **核心资产**：当前积分余额 |
| `level` | TINYINT | Default 1 | **会员等级**：1=T1, 2=T2, ..., 5=T5 |
| `role` | ENUM | 'user', 'admin' | 角色权限：普通用户/管理员 |
| `status` | TINYINT | Default 1 | 账号状态：1=正常, 0=封禁 |
| `register_ip` | VARCHAR(45) | Nullable | 注册时的 IP (用于风控) |
| `last_login_at` | DATETIME | Nullable | 最后登录时间 |
| `created_at` | DATETIME | Default Current | 注册时间 |


+ **索引建议**：
+ `UNIQUE INDEX idx_email (email)`
+ `INDEX idx_balance (balance)` (方便查询余额异常)



---

#### 表名：`membership_configs` (等级权益配置表)
**描述**：定义 T1 到 T5 每个等级的具体权限（并发数、队列权重），**支持后台动态调整**，无需硬编码。

| 字段名 | 类型 | 属性 | 描述 |
| --- | --- | --- | --- |
| `level` | TINYINT | PK | 等级 ID：1, 2, 3, 4, 5 |
| `name` | VARCHAR(20) | Not Null | 等级名称：T1, T2, ..., T5 |
| `concurrency_limit` | INT | Not Null | **并发槽位**：该等级允许同时运行的任务数 (如 T1=1, T5=5) |
| `queue_priority` | INT | Default 0 | 队列权重：数值越大，在 Worker 中优先级越高 |
| `remark` | VARCHAR(100) | Nullable | 备注 (如: "普通会员", "至尊会员") |


+ **初始化数据示例**：
+ (1, 'T1', 1, 0, '基础用户')
+ (3, 'T3', 3, 10, '进阶用户')
+ (5, 'T5', 5, 20, '顶级用户')



---

### 2. 任务与模型核心表
#### 表名：`tasks` (生成任务表)
**描述**：记录所有 AI 生成任务的状态、参数和结果。

| 字段名 | 类型 | 属性 | 描述 |
| --- | --- | --- | --- |
| `id` | VARCHAR(36) | PK | **任务 ID** (使用 UUID，防止被遍历) |
| `user_id` | INT | Not Null, FK | 关联用户 ID |
| `model_name` | VARCHAR(50) | Not Null | 模型标识 (如 'sora-v2', 'midjourney-v6') |
| `prompt` | TEXT | Nullable | 用户的提示词 (用于记录和风控) |
| `input_file_url` | TEXT<br/> | Nullable<br/> | 参考图地址 |
| `params` | JSON | Nullable | **动态参数**：存储时长、比例、画质等 JSON 数据 |
| `status` | ENUM | Default 'pending' | 状态：`pending`(排队), `processing`(执行中), `success`(成功), `failed`(失败) |
| `result_url` | TEXT | Nullable | **结果链接**：直接存储上游返回的 URL (不转存文件) |
| `cost_points` | DECIMAL(10, 2) | Not Null | 实际消耗/预扣除的积分 |
| `fail_reason` | VARCHAR(255) | Nullable | 失败原因 (展示给用户，如"内容违规") |
| `created_at` | DATETIME | Default Current | 提交时间 |
| `finished_at` | DATETIME | Nullable | 完成/失败时间 |


+ **索引建议**：
+ `INDEX idx_user_status (user_id, status)` (**关键索引**：用于快速统计用户当前有多少个 `processing` 任务，实现并发拦截)
+ `INDEX idx_created_at (created_at)` (用于数据统计)



---

#### 表名：`model_pricing` (模型定价表)
**描述**：管理不同模型的计费倍率。

| 字段名 | 类型 | 属性 | 描述 |
| --- | --- | --- | --- |
| `model_key` | VARCHAR(50) | PK | 模型唯一标识 (如 'sora-v2') |
| `base_cost` | DECIMAL(10, 2) | Not Null | 单次调用基础扣费 (如 500.00) |
| `is_active` | TINYINT | Default 1 | 是否上架 (1=上架, 0=维护中) |
| `config` | JSON | Nullable | 扩展配置 (如最大时长限制) |


---

### 3. 资产与支付核心表
#### 表名：`cdk` (兑换码表)
**描述**：存储积分充值卡密。

| 字段名 | 类型 | 属性 | 描述 |
| --- | --- | --- | --- |
| `id` | INT | PK, AI | 自增 ID |
| `code` | VARCHAR(32) | UK, Not Null | **兑换码** (唯一，加索引) |
| `points` | INT | Not Null | 面额 (积分数) |
| `type` | ENUM | 'once', 'universal' | 类型：`once`(一次性), `universal`(通用/活动码) |
| `batch_no` | VARCHAR(50) | Nullable | 批次号 (方便管理员按批次作废) |
| `status` | TINYINT | Default 0 | 状态：0=未使用, 1=已使用, 2=已作废 |
| `used_by` | INT | Nullable | 使用者 ID (仅 `once` 类型有效) |
| `used_at` | DATETIME | Nullable | 使用时间 |
| `expire_at` | DATETIME | Nullable | 过期时间 |


+ **索引建议**：
+ `UNIQUE INDEX idx_code (code)` (查询性能核心)



---

#### 表名：`transactions` (资金流水表)
**描述**：记录每一笔积分变动，用于审计和回溯。

| 字段名 | 类型 | 属性 | 描述 |
| --- | --- | --- | --- |
| `id` | INT | PK, AI | 流水 ID |
| `user_id` | INT | Not Null, FK | 用户 ID |
| `type` | ENUM | Not Null | 类型：`recharge`(充值), `task_cost`(任务消费), `refund`(失败退款), `system`(系统赠送) |
| `amount` | DECIMAL(10, 2) | Not Null | 变动金额 (正数为增，负数为减) |
| `balance_snapshot` | DECIMAL(10, 2) | Not Null | **余额快照**：变动后的余额 (方便核对) |
| `related_id` | VARCHAR(50) | Nullable | 关联 ID (充值填 cdk_id, 消费填 task_id) |
| `remark` | VARCHAR(255) | Nullable | 备注 (如 "Sora生成-5s-高清") |
| `created_at` | DATETIME | Default Current | 发生时间 |


+ **索引建议**：
+ `INDEX idx_user_created (user_id, created_at)` (用户查看账单)

### 4. Redis 数据结构设计 (补充)
虽然您要求数据库设计，但 **“单点登录”** 和 **“任务队列”** 必须依赖 Redis，以下是 Key 的设计规范：

#### A. 鉴权与风控
+ **单点登录互斥 (顶号)**：
+ `Key`: `auth:token:{user_id}`
+ `Value`: `{current_jwt_string}`
+ `TTL`: 7天 (与 JWT 有效期一致)
+ _逻辑：每次请求校验 Header 中的 Token 是否等于 Redis 中的 Value。_
+ **注册验证码**：
+ `Key`: `verify:email:{email}`
+ `Value`: `{code}`
+ `TTL`: 300秒



#### B. 任务队列 (优先级通道)
+ **T4-T5 专用通道**：
+ `Key`: `queue:tasks:high`
+ `Type`: List
+ **T1-T3 普通通道**：
+ `Key`: `queue:tasks:normal`
+ `Type`: List
+ _逻辑：Worker 优先 _`RPOP`_ high 队列，为空时再取 normal。_



#### C. 系统配置缓存
+ **模型定价缓存**：
+ `Key`: `config:pricing`
+ `Value`: JSON String (从 MySQL `model_pricing` 同步)
+ _逻辑：防止每次计算扣费都查数据库。_

### 5. ER 图关系简述
1. `users.level` **关联** `membership_configs.level` (定义权限)
2. `users.id` **1:N** `tasks.user_id` (一个用户多个任务)
3. `users.id` **1:N** `transactions.user_id` (一个用户多条流水)
4. `users.id` **1:N** `cdk.used_by` (一个用户兑换多个 CDK)
5. `tasks.id` **逻辑关联** `transactions.related_id` (消费流水对应具体任务)
