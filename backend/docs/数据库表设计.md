这是一个基于 MySQL 的详细数据库表结构设计。

设计遵循了**“T1-T5 等级制度”**、**“不转存文件（直接存上游链接）”**、**“高并发任务管理”**以及**“积分资产安全”**的核心需求。

---

### 1. 用户与权限核心表
#### 表名：`users` (用户表)
**描述**：存储用户基础信息、当前等级、积分余额。

| 字段名 | 类型 | 属性 | 描述 |
| --- | --- | --- | --- |
| `id` | INT | PK, AI | 用户唯一 ID |
| `email` | VARCHAR(100) | UK, Not Null | 登录邮箱 (唯一索引) |
| `name` | VARCHAR(50) | Nullable | 用户名 (显示名称) |
| `password_hash` | VARCHAR(255) | Not Null | 加盐加密后的密码 |
| `balance` | DECIMAL(10, 2) | Default 0.00 | **核心资产**：当前积分余额 |
| `level` | TINYINT | Default 1 | **会员等级**：1=T1, 2=T2, ..., 5=T5 |
| `role` | ENUM | 'user', 'admin' | 角色权限：普通用户/管理员 |
| `status` | TINYINT | Default 1 | 账号状态：1=正常, 0=封禁 |
| `register_ip` | VARCHAR(45) | Nullable | 注册时的 IP (用于风控) |
| `last_login_at` | DATETIME | Nullable | 最后登录时间 |
| `created_at` | DATETIME | Default Current | 注册时间 |


+ **索引建议**：
+ `UNIQUE INDEX idx_email (email)`
+ `INDEX idx_balance (balance)` (方便查询余额异常)

#### 表名：`membership_configs` (等级权益配置表)
**描述**：定义 T1 到 T5 每个等级的具体权限（并发数、队列权重），**支持后台动态调整**，无需硬编码。

| 字段名 | 类型 | 属性 | 描述 |
| --- | --- | --- | --- |
| `level` | TINYINT | PK | 等级 ID：1, 2, 3, 4, 5 |
| `name` | VARCHAR(20) | Not Null | 等级名称：T1, T2, ..., T5 |
| `concurrent_limit` | INT | Not Null | **并发槽位**：该等级允许同时运行的任务数 (如 T1=1, T5=20) |
| `queue_weight` | INT | Default 1 | 队列权重：数值越大，在 Worker 中优先级越高 |
| `price` | DECIMAL(10, 2) | Default 0.00 | **月费价格**：该等级的月订阅费用（元），0 表示免费 |
| `description` | VARCHAR(100) | Nullable | 等级描述 (如: "免费用户", "至尊会员") |


+ **初始化数据示例**：
+ (1, 'T1', 1, 1, 0.00, '免费用户')
+ (2, 'T2', 3, 2, 29.00, '基础会员')
+ (3, 'T3', 5, 3, 99.00, '高级会员')
+ (4, 'T4', 10, 4, 299.00, '专业会员')
+ (5, 'T5', 20, 5, 999.00, '旗舰会员')

### 2. 任务核心表
#### 表名：`tasks` (生成任务表)
**描述**：记录所有 AI 生成任务的状态、参数和结果。

| 字段名 | 类型 | 属性 | 描述 |
| --- | --- | --- | --- |
| `id` | VARCHAR(36) | PK | **任务 ID** (使用 UUID，防止被遍历) |
| `user_id` | INT | Not Null, FK | 关联用户 ID |
| `model` | VARCHAR(50) | Not Null | **模型标识** (如 'openai', 'sora')，关联 models.key |
| `prompt` | TEXT | Nullable | 用户的提示词 (用于记录和风控) |
| `input_file_url` | TEXT | Nullable | 参考图地址 |
| `params` | JSON | Nullable | **动态参数**：存储时长、比例、画质等 JSON 数据 |
| `status` | ENUM | Default 'pending' | 状态：`pending`(排队), `processing`(执行中), `success`(成功), `failed`(失败), `cancelled`(已取消) |
| `progress` | SMALLINT | Default 0 | **任务进度**：0-100，执行中实时更新 |
| `upstream_task_id` | VARCHAR(255) | Nullable | **上游任务ID**：上游API返回的任务标识，用于轮询进度 |
| `result_url` | TEXT | Nullable | **结果链接**：直接存储上游返回的 URL (不转存文件) |
| `cost_points` | DECIMAL(10, 2) | Not Null | 实际消耗/预扣除的积分 |
| `token_usage` | JSON | Nullable | Token 使用情况：{"input": 1000, "output": 500} |
| `api_key_id` | INT | Nullable | 使用的密钥 ID（关联 api_keys.id） |
| `fail_reason` | VARCHAR(255) | Nullable | 失败原因 (展示给用户，如"内容违规") |
| `created_at` | DATETIME | Default Current | 提交时间 |
| `finished_at` | DATETIME | Nullable | 完成/失败时间 |


+ **索引建议**：
+ `INDEX idx_user_status (user_id, status)` (**关键索引**：用于快速统计用户当前有多少个 `processing` 任务，实现并发拦截)
+ `INDEX idx_model (model)` (按模型统计任务)
+ `INDEX idx_upstream_task_id (upstream_task_id)` (通过上游任务ID反查本地任务)
+ `INDEX idx_created_at (created_at)` (用于数据统计)


+ **字段说明**：
+ `id`：本地任务ID，前端使用此ID查询任务状态
+ `upstream_task_id`：上游API返回的任务ID，Worker使用此ID轮询上游进度
+ `progress`：任务执行进度（0-100），pending时为0，processing时实时更新，完成时为100
+ `status`：新增 `cancelled` 状态支持用户主动取消任务

#### 表名：`models` (模型基本信息表)
**描述**：存储所有AI模型的基本信息，用于前端动态渲染。

| 字段名 | 类型 | 属性 | 描述 |
| --- | --- | --- | --- |
| `key` | VARCHAR(50) | PK | 模型唯一标识 (如 'openai', 'sora') |
| `name` | VARCHAR(100) | Not Null | 模型显示名称 (如 'OpenAI', 'Sora') |
| `enabled` | TINYINT | Default 1 | 是否启用：1=启用, 0=禁用 |
| `description` | TEXT | Nullable | 模型描述信息 |
| `color` | VARCHAR(50) | Nullable | UI 颜色标识 (如 'bg-green-500') |
| `icon_url` | VARCHAR(255) | Nullable | 模型图标 URL |
| `max_concurrency_limit` | INT | Default 20 | 建议的最大并发限制 |
| `tags` | JSON | Nullable | **模型分类标签**：字符串数组，如 `["video", "generation"]` |
| `created_at` | DATETIME | Default Current | 创建时间 |
| `updated_at` | DATETIME | On Update Current | 更新时间 |


+ **索引建议**：
+ `INDEX idx_enabled (enabled)` (快速查询启用的平台)


+ **tags字段说明**：
+ 存储格式：JSON字符串数组，如 `["video", "generation"]`
+ 用途：前端筛选和分类展示模型
+ 允许为空或空数组 `[]`
+ 推荐的标签体系：
  - 类型维度：video, image, text, audio
  - 功能维度：generation, edit, chat, transcription
  - 特性维度：hd, realtime, multimodal


+ **初始化数据示例**：
+ ('sora-2', 'Sora 2.0', 1, 'OpenAI Sora 视频生成模型', 'bg-blue-500', NULL, 10, '["video", "generation"]', ...)
+ ('gpt-4', 'GPT-4', 1, 'OpenAI GPT-4 对话模型', 'bg-green-500', NULL, 20, '["text", "chat", "multimodal"]', ...)
+ ('dall-e-3', 'DALL-E 3', 1, 'OpenAI 图像生成模型', 'bg-purple-500', NULL, 15, '["image", "generation"]', ...)

#### 表名：`model_configs` (模型配置表)
**描述**：配置每个模型的等级权限和计费规则（替代原 model_pricing 表）。

| 字段名 | 类型 | 属性 | 描述 |
| --- | --- | --- | --- |
| `id` | INT | PK, AI | 配置 ID |
| `model` | VARCHAR(50) | UK, Not Null | 模型标识（外键关联 models.key） |
| `allowed_tiers` | JSON | Not Null | 允许使用的等级数组 (如 ["T1","T2","T3","T4","T5"]) |
| `cost_per_call` | DECIMAL(10, 2) | Default 0.00 | 固定计费：每次调用扣除积分 |
| `token_cost_config` | JSON | Nullable | Token 计费配置：{"enabled": true, "input_cost": 0.03, "output_cost": 0.06} |
| `params` | JSON | Nullable | 模型自定义参数（用于前端渲染可选项，例如 {"durations":[10,15], "hd_supported": true}） |
| `is_active` | TINYINT | Default 1 | 是否启用：1=启用, 0=禁用 |
| `description` | TEXT | Nullable | 配置说明 |
| `created_at` | DATETIME | Default Current | 创建时间 |
| `updated_at` | DATETIME | On Update Current | 更新时间 |


+ **索引建议**：
+ `UNIQUE INDEX idx_model (model)` (每个模型只有一个配置)
+ `INDEX idx_active (is_active)` (查询启用的模型配置)


+ **计费逻辑说明**：
+ 总扣费 = `cost_per_call` + (如果启用 Token 计费) (input_tokens/1000 * input_cost + output_tokens/1000 * output_cost)


 + **初始化数据示例**：
 + (1, 'openai', '["T1","T2","T3","T4","T5"]', 10.00, '{"enabled":true,"input_cost":0.03,"output_cost":0.06}', 1, ...)
 + (2, 'sora', '["T3","T4","T5"]', 100.00, '{"enabled":false}', 1, '{"durations":[10,15],"hd_supported":true}')
 + (3, 'midjourney', '["T2","T3","T4","T5"]', 50.00, '{"enabled":false}', 1, '{"durations":[5,10],"hd_supported":false}')

#### 表名：`api_keys` (密钥池管理表)
**描述**：存储上游 API 密钥，支持并发控制、熔断机制、负载均衡（基于 MySQL + Redis 双层架构）。

| 字段名 | 类型 | 属性 | 描述 |
| --- | --- | --- | --- |
| `id` | INT | PK, AI | 密钥 ID |
| ~~`model`~~ | ~~VARCHAR(50)~~ | ~~Not Null~~ | **已移除**：改为多对多关联 (见 `api_key_models` 表) |
| `api_base` | VARCHAR(512) | Not Null | **API 基础地址** (默认官方地址，支持中转) |
| `key_secret` | VARCHAR(512) | Not Null | **密钥本体** (建议加密存储) |
| `max_concurrency` | INT | Default 3 | **最大并发限制**：该密钥同时运行的最大任务数 |
| `weight` | TINYINT | Default 10 | 权重 (1-100)：用于负载均衡轮询 |
| `status` | TINYINT | Default 1 | 状态：1=启用, 0=停用 |
| `total_calls` | INT | Default 0 | 累计调用次数 |
| `total_errors` | INT | Default 0 | 累计失败次数 |
| `last_used_at` | DATETIME | Nullable | 最后使用时间 |
| `created_at` | DATETIME | Default Current | 添加时间 |
| `updated_at` | DATETIME | On Update Current | 更新时间 |


+ **索引建议**：
+ ~~`INDEX idx_model_status (model, status)`~~ **已废弃**
+ `INDEX idx_status (status)` (**新增**：查询启用的密钥)
+ `INDEX idx_weight (weight)` (负载均衡选择)


+ **Redis 实时状态**（不存储在 MySQL）：
+ `redis:pool:usage:{key_id}` → 当前并发数 (String, TTL: 24小时)
+ `redis:pool:cooldown:{key_id}` → 冷却结束时间戳 (String, TTL: 冷却时长)
+ `redis:pool:stats:calls:{key_id}` → 调用统计缓冲 (String, 定时同步到 MySQL)
+ `redis:pool:stats:errors:{key_id}` → 错误统计缓冲 (String, 定时同步到 MySQL)


+ **初始化数据示例**：
+ (1, 'https://api.openai.com/v1', 'sk-proj-abc...', 5, 10, 1, 0, 0, NULL, ...)
+ (2, 'https://ai.t8star.cn/v2/videos/generations', 'sk-sora-xyz...', 2, 5, 1, 0, 0, NULL, ...)

#### 表名：`api_key_models` (密钥与模型关联表) **新增**
**描述**：实现 ApiKey 与 Model 的多对多关系，一个密钥可以服务多个模型，每个模型可以有独立的 API 端点。

| 字段名 | 类型 | 属性 | 描述 |
| --- | --- | --- | --- |
| `id` | INT | PK, AI | 关联 ID |
| `api_key_id` | INT | FK, Not Null | 密钥 ID（关联 `api_keys.id`） |
| `model` | VARCHAR(50) | FK, Not Null | 模型标识（关联 `models.key`） |
| `api_base` | VARCHAR(512) | Not Null, Default '' | **该模型的 API 端点地址**（如 `https://ai.t8star.cn/v2/videos/generations`） |
| `created_at` | DATETIME | Default Current | 创建时间 |


+ **索引建议**：
+ `UNIQUE KEY uk_key_model (api_key_id, model)` (**核心索引**：防止重复关联)
+ `INDEX idx_model (model)` (**关键索引**：按模型查询密钥，高频查询)
+ `INDEX idx_api_key_id (api_key_id)` (辅助查询)


+ **外键约束**：
+ `FOREIGN KEY (api_key_id) REFERENCES api_keys(id) ON DELETE CASCADE`
+ `FOREIGN KEY (model) REFERENCES models(key) ON DELETE CASCADE`


+ **设计说明**：
+ 引入 `api_base` 字段的原因：
  - 同一个 API 密钥可能对应多个模型，但不同模型的端点地址可能不同
  - 例如：t8star 的视频生成用 `/v2/videos/generations`，图片生成用 `/v1/images/generations`
  - 通过在关联表中存储 api_base，实现每个 (密钥, 模型) 组合有独立的端点配置


+ **初始化数据示例**：
+ (1, 1, 'sora-video', 'https://ai.t8star.cn/v2/videos/generations', ...)  # 密钥1的视频生成端点
+ (2, 1, 'sora-image', 'https://ai.t8star.cn/v1/images/generations', ...)  # 密钥1的图片生成端点
+ (3, 2, 'gpt-4', 'https://api.openai.com/v1', ...)  # 密钥2支持 OpenAI 统一端点

### 4. Redis 数据结构设计 (补充)
虽然您要求数据库设计，但 **“单点登录”** 和 **“任务队列”** 必须依赖 Redis，以下是 Key 的设计规范：

#### A. 鉴权与风控
+ **单点登录互斥 (顶号)**：
+ `Key`: `auth:token:{user_id}`
+ `Value`: `{current_jwt_string}`
+ `TTL`: 7天 (与 JWT 有效期一致)
+ _逻辑：每次请求校验 Header 中的 Token 是否等于 Redis 中的 Value。_
+ **注册验证码**：
+ `Key`: `verify:email:{email}`
+ `Value`: `{code}`
+ `TTL`: 300秒



#### B. 任务队列 (优先级通道)
+ **T4-T5 专用通道**：
+ `Key`: `queue:tasks:high`
+ `Type`: List
+ **T1-T3 普通通道**：
+ `Key`: `queue:tasks:normal`
+ `Type`: List
+ _逻辑：Worker 优先 _`RPOP`_ high 队列，为空时再取 normal。_



#### C. 系统配置缓存
+ **模型配置缓存**：
+ `Key`: `config:models`
+ `Value`: JSON String (从 MySQL `models` 表同步)
+ _逻辑：防止每次查询都读数据库。_

+ **模型计费配置缓存**：
+ `Key`: `config:model_configs`
+ `Value`: JSON String (从 MySQL `model_configs` 表同步)
+ _逻辑：用于快速计算任务扣费。_

### 5. ER 图关系简述

#### A. 用户相关
1. `users.level` **关联** `membership_configs.level` (定义权限)
2. `users.id` **1:N** `tasks.user_id` (一个用户多个任务)
3. `users.id` **1:N** `transactions.user_id` (一个用户多条流水)
4. `users.id` **1:N** `cdk.used_by` (一个用户兑换多个 CDK)

#### B. 模型相关
5. `models.key` **1:1** `model_configs.model` (模型基本信息 ↔ 模型配置)
6. ~~`models.key` **1:N** `api_keys.model`~~ **已废弃**
   **新增**: `models.key` **M:N** `api_keys.id` (通过 `api_key_models` 关联表)
7. `models.key` **1:N** `tasks.model` (一个模型多个任务)

#### C. 任务相关
8. `tasks.model` **关联** `models.key` (任务使用的模型)
9. `tasks.api_key_id` **关联** `api_keys.id` (任务使用的密钥)

#### D. 配置关联
11. `model_configs.model` **关联** `models.key` (模型配置关联模型)
12. `model_configs.allowed_tiers` **JSON 关联** `membership_configs.name` (允许的会员等级)

### 6. 核心业务流程

#### A. 用户创建任务流程
1. 用户提交任务 → 检查 `users.level` 对应的 `membership_configs.concurrent_limit`
2. 查询 `tasks` 表统计当前 `processing` 任务数，判断是否超过并发限制
3. 查询 `model_configs` 检查用户等级是否在 `allowed_tiers` 中
4. 计算扣费：`model_configs.cost_per_call` + Token 费用
5. 预扣积分，创建 `tasks` 记录，写入 `transactions` 流水

#### B. 任务分配密钥流程
1. Worker 从 Redis 队列取出任务
2. 查询 `api_keys` 表：`model = task.model AND status = 1`
3. 通过 Redis 检查每个密钥的实时并发数 `redis:key:{id}:concurrency`
4. 过滤掉正在冷却的密钥 `redis:key:{id}:cooling`
5. 基于 `weight` 字段进行加权随机选择
6. 更新 `tasks.api_key_id`，Redis 并发数 +1

#### C. 任务完成流程
1. Worker 收到上游结果 → 更新 `tasks.status` 和 `result_url`
2. 如果启用 Token 计费，根据 `token_usage` 追加扣费
3. 更新 `api_keys.total_calls`，Redis 并发数 -1
4. 如果失败，退款并更新 `transactions` 表
